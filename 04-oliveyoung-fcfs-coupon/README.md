# 04. 올리브영 「올영세일 선착순 쿠폰, 미발급 0%를 향한 여정」 재현

> 원문: [올영세일 선착순 쿠폰, 미발급 0%를 향한 여정 — Redis와 Message Queue로 구축한 비동기 시스템의 정합성 개선기](https://oliveyoung.tech/2025-12-15/fcfs-coupon/) (올리브영 테크블로그, 2025-12-15)

## 원문 요약

- **구조:** 선착순 쿠폰 발급은 MQ 기반 비동기다. 온라인몰(앞단)이 Redis에서 발급 수량을 읽어 1차 유효성 검사를 하고, 통과하면 Message Queue에 메시지를 발행한 뒤 사용자에게 "발급 성공"으로 응답한다. 발급 워커가 메시지를 받아 2차 유효성 검사를 하고 쿠폰을 최종 발급한다(DB). 수량은 DB 대신 Redis에 쿠폰별 키로 두고 쿠폰 유효 기간만큼 TTL을 건다.
- **장애:** 2025년 6월 올영세일(7일) 동안 워커의 2차 검사가 실패해 쿠폰이 발급되지 않은 건이 생겼다. 사용자는 이미 "발급 성공" 응답을 받았으니 CS 문의로 이어졌다. 평균 미발급률 약 0.014%(10,000건당 1.4건), 일차별 0.004~0.037%.
- **원인 세 가지:**
  1. **Time Gap:** 1차 검증(T0)과 워커의 재검증(T3) 사이에 MQ 발행·수신 지연이 있다. 그 사이 수백 건이 몰리면 1차를 통과한 요청이 2차에서 떨어진다.
  2. **이중 검증 오버헤드:** 워커의 재검증은 필요하지만, Time Gap 때문에 앞단의 1차 검증이 무의미해진다.
  3. **Redis GET/INCR 원자성 부재:** 수량을 읽는 `GET`과 올리는 `INCR`이 별도 명령이라 그 사이에 다른 요청이 끼어든다. 수량 오버플로우(과발급)가 난다.
- **개선 시도:**
  1. **발급 수량 선차감:** `INCR`을 워커가 아닌 앞단에서 한다(Time Gap 줄이기). 워커의 DB 처리가 실패하면 되돌린다. 미발급이 줄었지만 남았다. `GET`과 `INCR`이 떨어져 있는 한 경합이 막히지 않아서다.
  2. **Lua 스크립트:** `GET`·비교·`INCR`을 스크립트 하나로 묶어 원자적으로 실행한다. 미발급·과발급 0건이 됐지만 성능이 약 21% 떨어져 기각했다(Redis가 싱글 스레드라 스크립트가 도는 동안 다른 요청이 기다린다. 디버깅·모니터링도 어렵다).
  3. **이중 카운터:** 요청 수량 키(`coupon:{id}:countReq`)를 먼저 올려 동시 요청을 걸러 내고, 통과한 요청만 실제 발급 수량 키(`coupon:{id}:count`)를 올린다. Lua 없이 명령 2개로 해결하며 성능 저하는 약 8%였다. 워커로 넘어가는 초과 발급은 0건.
- **최종:** 1번 + 3번. 개발 환경 부하 테스트(제한 10,000건)에서 발급 성공 응답 10,162건 → 10,000건, 미발급 162건(1.62%) → 0건. 9월 올영세일에서 기능 플래그를 4일차부터 켜니 미발급 0건, 처리량 저하 없음.
- **운영 고려:** 키 네이밍과 TTL(쿠폰 종료 + 1시간), `count`와 `countReq`의 차이 모니터링과 알람, Redis 장애 시 DB fallback, 두 수량이 어긋나면 정합성 보정.
- **원문 환경:** Kotlin + `RedisTemplate`, Message Queue는 RabbitMQ(원문이 링크한 "쿠폰 발급 RabbitMQ 도입기"), DB. 버전은 밝히지 않았다. 원문의 그림(발급 흐름, 수량 차감 흐름도)은 이미지라 글에 적힌 설명으로 구조를 세웠다.

## 장애 연쇄

```
세일이 열리고 발급 요청이 ms 단위로 몰린다
  ▼ 온라인몰: Redis GET으로 수량을 읽어 1차 검증. 아직 남았다 → MQ에 발행하고 사용자에게 "발급 성공" 응답
  ▼ 같은 순간 들어온 다른 요청들도 같은 수량을 보고 통과한다 (수량을 올리는 INCR은 워커의 일이라 아무도 올리지 않았다)
  ▼ 워커가 메시지를 받을 때는 앞서 받은 요청들이 수량을 다 썼다 (Time Gap) → 2차 검증 실패 → 미발급
  ▼ 워커끼리도 GET과 INCR이 떨어져 있어 경합한다 → 제한을 넘겨 발급 (과발급)
  ▼ "발급 성공"을 본 고객에게 쿠폰이 없다 → CS 문의
```

## 실험 환경

```
k6 ─ 서로 다른 사용자가 같은 쿠폰의 발급을 한꺼번에(0단계, k6/issue.js) 또는 초당 일정 속도로(1단계부터, k6/load.js) 요청
 │
 ▼
POST /coupons/{couponId}/issue?userId=N        온라인몰(앞단). Redis GET으로 1차 검증 → 통과하면 MQ에 발행하고 200 SUCCESS, 마감이면 409 SOLD_OUT
POST /experiments/reset?couponId=C001&limit=N  실험용: 큐·DB·Redis 수량·집계를 모두 비우고 제한 수량이 N인 쿠폰을 만든다
GET  /experiments/summary?couponId=C001        실험용: 성공 응답 수, 실제 발급 수, 미발급 수, 과발급 수, 큐 잔량, Time Gap
GET  /experiments/progress?couponId=C001       실험용: 실행 중 0.1초마다 읽는 진행 상태(성공·마감 응답, 발급 누계, 워커 처리 완료, 큐 대기) (1단계부터)
 │
 ▼
app 컨테이너 (Spring Boot)
 IssueService(앞단) ─ GET coupon:C001:count ─▶ RabbitMQ 큐 coupon-issue ─▶ IssueWorker (소비자 8개)
                                                                              ├ GET coupon:C001:count  2차 검증. 마감이면 issue_failures에 기록 (= 미발급)
                                                                              └ INCR coupon:C001:count → MySQL coupon_issues에 저장 (= 발급)
```

- Redis 키는 원문의 이름(`coupon:{couponId}:count`)을 쓰고, 처음 만들 때 쿠폰 종료 시각까지의 TTL을 건다.
- 발급 워커는 원문에서 별도 인스턴스지만 여기서는 같은 앱 안의 리스너 소비자 스레드로 둔다. 소비자 수가 "워커 몇 대가 동시에 처리하는가"다.
- 원문의 유저별 키(1인 1매 확인)는 넣지 않았다. k6가 사용자마다 한 번씩만 요청한다.
- 집계의 뜻: `successResponses`(발급 성공 응답) = `issued`(실제 발급, DB) + `unissued`(워커 2차 검증 실패, DB). `overIssued` = `issued` − 제한 수량. `queued`가 0이어야 워커가 다 처리한 뒤의 집계다.

## 0단계: 사전 확인 결과

- **원문의 코드 패턴이 최신 버전에서도 그대로다.** Spring Data Redis 4.1.1의 `opsForValue().get()`은 `GET`, `increment()`는 `INCR` 한 번씩이고 둘을 묶어 주는 것은 없다. 초기화 뒤 발급 요청 1건을 보내며 `redis-cli MONITOR`로 보면 `GET`(앞단 1차 검증) → `GET`(워커 2차 검증) → `INCR`(워커) → `PEXPIREAT`(처음 만든 키의 TTL) 순서로 네 명령이 온다. `expireAt(Instant)`는 `EXPIREAT`가 아니라 밀리초 단위 `PEXPIREAT`로 나간다.
- **재현 확인** (Claude 검증, `results/claude-verification/stage0/`). 쿠폰 하나에 서로 다른 사용자가 한꺼번에 요청했다. 모두 워커 소비자 4개(기본값)다.

  | 제한 수량 | 요청 수 (동시 사용자) | 발급 성공 응답 | 실제 발급 | 미발급 | 과발급 | Time Gap 최소 / 평균 / 최대 |
  |---|---|---|---|---|---|---|
  | 100 | 300 (100) | 300 | 100 | 200 | 0 | 47ms / 168ms / 256ms |
  | 10,000 | 12,000 (200) | 12,000 | 10,000 | 2,000 | 0 | 18ms / 4.8초 / 6.3초 |

  - **원문의 미발급이 생긴다.** 요청 전부가 "발급 성공"을 받았지만 발급은 제한 수량까지였다. 1차 검증은 한 번도 마감(409)을 돌려주지 않았다. 워커가 수량을 올리기 전에 요청이 모두 들어왔기 때문이다.
  - **미발급 비율은 원문보다 훨씬 높았다.** 원문의 부하 테스트는 성공 응답 10,162건에 미발급 162건(1.62%)이었는데, 여기서는 12,000건에 2,000건이다. 원문은 워커가 거의 따라가는 상태(Time Gap 수십 ms)였고, 여기서는 워커가 요청 속도(초당 약 1,900~2,300건)를 따라가지 못해 큐가 쌓였다(Time Gap 평균 4.8초). 미발급 수는 Time Gap 동안 1차를 통과한 요청 수다. 1단계에서 요청 속도와 워커 동시 처리 수를 원문 규모에 맞춘다.
  - **과발급은 기본 설정에서는 0건이었다.** 워커 소비자를 32개로 올리면(`WORKER_CONCURRENCY=32`) 제한 100에 요청 300을 5번 보냈을 때 4번에서 9·13·14·21건이 넘게 발급됐다(`results/claude-verification/stage0/exploration/`). 원문이 든 "GET/INCR 원자성 부재 → 수량 오버플로우"도 최신 버전에서 생긴다. 왜 소비자 수에 따라 다른지는 2단계에서 본다.
- **Time Gap은 요청이 적어도 있다.** 요청 1건의 1차 검증 통과부터 워커 수신까지 약 12~50ms였다(MQ 발행·수신과 소비자 스레드 깨우기). 원문 그림의 "MQ 발행 10ms, Worker 수신 50ms"와 비슷한 크기다.
- **원문과 다른 점·줄인 것:** Kotlin 대신 Java. 워커는 별도 인스턴스가 아니라 같은 앱의 소비자 스레드. 유저별 키(1인 1매)와 워커의 DB 처리 실패(원문 시도 1의 롤백)는 넣지 않았다. 원문의 시도 1~3은 3단계에서 스위치로 더한다.

## 1단계: 재현

원문의 부하 테스트처럼 제한 수량 10,000개인 쿠폰에 그보다 많은 사용자가 요청한다. 0단계에서 미발급 수가 "워커가 요청을 얼마나 따라가느냐"에 달려 있었다. 그래서 워커는 그대로 두고(소비자 8개) 요청 속도만 바꿔 두 상태를 본다. 요청 수는 둘 다 20,000건이다.
- **1-A 요청이 워커보다 빠를 때:** 초당 1,000건 × 20초. 워커 뒤로 요청이 쌓인다.
- **1-B 워커가 따라갈 때:** 초당 500건 × 40초. 원문 운영처럼 워커가 거의 바로 처리한다.

| `k6/load.js` | 초당 `RATE`건씩 `DURATION` 동안 요청한다. 요청마다 다른 사용자다. 서버가 느려져도 도착 속도가 유지되는 open model이라, 선착순 오픈처럼 "서버가 느려졌다고 요청이 줄지는 않는" 상황이다 |

리포트 읽는 법
- **결과 블록:** 발급 성공 응답(앞단이 200을 돌려준 수) = 실제 발급(DB) + 미발급(워커 2차 검증 실패). 미발급률은 원문처럼 제한 수량 기준으로도, 성공 응답 기준으로도 적는다. 과발급 = 실제 발급 − 제한 수량. Time Gap = 1차 검증 통과부터 워커 수신까지.
- **시간표(0.5초 단위, 모두 누계):** `성공 응답`·`마감 응답`은 k6가 받은 응답, `발급(Redis)`은 워커가 올린 수량, `워커 미처리`는 성공 응답 중 워커가 아직 처리를 끝내지 않은 수(괄호는 그중 큐에서 기다리는 수. 나머지는 워커가 미리 가져가 손에 든 것). `◀` 표시는 발급이 제한 수량에 닿은 칸이다.
- `주의`가 찍히면 결과가 섞였거나 덜 끝난 것이다. 다시 돌린다.

### 바뀐 것

- `/experiments/progress`: 실행 중 0.1초마다 읽어도 가벼운 진행 상태(DB를 세지 않는다). 워커가 처리를 끝낸 수(`handled`)를 더했다. 큐 잔량만으로는 워커가 미리 가져간 메시지(prefetch 250개 × 소비자 수)가 빠져 밀린 양이 작게 보인다.
- **예열:** 막 뜬 앱은 JIT·채널·커넥션이 식어 있어 처음 수천 건이 몇 배 느리다. 실행기가 본 실행 전에 같은 경로로 8,000건(초당 1,000건 × 8초)을 흘린 뒤 다시 초기화한다.
- **RabbitMQ 발행 채널 캐시 25 → 200:** 캐시보다 동시 발행이 많으면 요청마다 채널을 열고 닫는다(브로커 왕복 2번, 캐시 잠금 안에서). 응답이 조금만 느려져 동시 요청이 25개를 넘으면 그 비용이 다시 응답을 늦춰 중앙값이 수 초까지 치솟았다. 스레드 덤프에서 Tomcat 스레드들이 `CachingConnectionFactory.findOpenChannel`의 잠금을 기다리고 있었다. 재현 대상이 아니라 Tomcat 스레드 수(200)만큼 캐시한다.
- **MySQL 연결의 TLS를 껐다**(`sslMode=DISABLED`): 워커가 발급마다 DB에 쓰는 비용에서 암호화 CPU를 뺀다.
- **워커 소비자 기본값 4 → 8:** 이 노트북(Docker VM CPU 5개)에서 소비자 4개는 초당 약 450~550건, 8개는 약 700건을 처리하고, 16개는 CPU 경합으로 오히려 느려졌다. 앞단은 초당 1,000건까지 받는다. 그래서 요청 초당 1,000건이면 워커가 밀리고, 500건이면 따라간다. 0단계의 표는 4개로 잰 값이다.
- 같은 조건이어도 실행마다 꽤 다르다. 앱이 1초 안팎 멈추는 때가 있어(p99 수백 ms) 미발급 수는 몇 배까지 달라진다. 숫자 하나보다 두 실행의 모양 차이를 본다.

### 1단계 결과

직접 실행(2026-10-15 15:05~15:08)한 값이다. 둘 다 `주의` 없이 끝났다. Claude가 검증하며 돌린 값은 `results/claude-verification/stage1/`에 있고 같은 모양이었다(1-A 미발급 1,180건, 1-B 1건).

| 관찰 항목 | 1-A 초당 1,000건 × 20초 | 1-B 초당 500건 × 40초 |
|---|---|---|
| 발급 성공 응답 / 마감 응답 | 11,259건 / 8,742건 | 10,001건 / 9,999건 |
| 실제 발급 / 미발급 (미발급률) / 과발급 | 10,001건 / 1,258건 (12.58%) / 1건 | 10,000건 / 1건 (0.01%) / 0건 |
| 발급이 제한 수량에 닿은 시각, 그때까지의 성공 응답 | +11.0~+11.5초, 11,259건 | +20.0~+20.5초, 10,001건 |
| 워커 미처리 최대 | 2,125건 (+5.5~+6.0초, 그중 큐 대기 126건) | 477건 (+2.5~+3.0초, 큐 대기 0건) |

**1단계에서 새로 알게 된 것**
- **원문의 미발급이 원문 규모에서 그대로 생겼다.** 1-A에서는 11,259명이 "발급 성공"을 받았지만 발급은 10,001건이라 1,258명(12.58%)이 쿠폰을 못 받았다. 1-B는 1명(0.01%)이었다. 원문의 부하 테스트(1.62%)는 둘 사이이고, 운영(0.014%)은 1-B에 가깝다.
- **미발급 수는 "발급이 제한 수량에 닿기 전까지의 성공 응답 − 제한 수량"이었다.** 1-A는 11,259 − 10,001 = 1,258건. 발급(Redis)이 10,000에 닿은 +11.25초까지 1차 검증은 한 건도 거르지 못했고, 마감 응답은 그 뒤에야 나왔다.
- **워커가 뒤처진 만큼 미발급이 늘었다.** 1-A는 워커 미처리가 2,125건까지 쌓이고 Time Gap 평균이 1.22초였다. 1-B는 477건, 105ms였다. 밀린 요청은 큐가 아니라 워커가 미리 가져간 버퍼에 있었다(큐 대기는 거의 0).
- **워커가 따라가도 0은 아니었다.** 1-B에서 1건이 남았다(Claude 검증도 1건). Time Gap이 0.2ms라도 0이 아닌 한 사라지지 않는다.
- **과발급은 1-A에서 1건 나왔다.** 1-B와 Claude 검증의 두 실행은 0건이었고, 실행기를 다듬으며 돌린 실행에서는 1~6건이 나왔다. 발급이 제한 수량에 닿는 순간에만 생길 수 있어 실행마다 다르다. 2단계에서 워커 소비자 수와 함께 본다.
- **같은 조건이어도 실행마다 꽤 달랐다.** 1-A 미발급이 직접 실행 1,258건, Claude 검증 1,180건이었고 Time Gap 평균은 1.22초와 857ms였다.

## 2단계: 원인 증명

원문이 든 세 원인을 요청마다 남긴 기록으로 하나씩 가른다. 2단계부터 앱은 요청마다 네 가지를 DB에 남긴다. **1차 검증 시각과 그때 본 수량**(앞단이 메시지에 실어 보낸다), **2차 검증 시각과 그때 본 수량**(워커), **`INCR`이 돌려준 값**. 이 기록으로 "1차 검증은 무엇을 보고 통과시켰고, 워커는 무엇을 보고 떨어뜨렸나"를 요청 하나하나 본다. 요청 경로의 Redis 명령은 그대로다(`GET`, `GET`, `INCR`).

| 원인 | 원문의 설명 | 보는 증거 |
|---|---|---|
| ① Time Gap | 1차 검증(T0)과 워커 재검증(T3) 사이의 간극에 요청이 몰려 T0 검증이 무의미해진다 | 요청마다 1차 → 2차 시간. 1차 검증이 본 수량과 실제로 앞서 통과한 요청 수의 차이("못 본 요청"). 미발급 요청의 1차·2차 시각이 "발급이 제한에 닿은 시각"의 앞인지 뒤인지 |
| ② 이중 검증 오버헤드 | 워커의 재검증은 필수지만 그 때문에 앞단의 1차 검증이 무의미해진다 | 1차 통과·실패 × 2차 통과·실패 표. 1차가 처음 마감을 돌려준 시각 |
| ③ GET/INCR 원자성 부재 | 두 명령 사이에 다른 요청이 끼어 수량이 넘친다 | 2차 검증에서 같은 수량을 읽은 요청 묶음. 과발급 요청과 같은 값을 읽은 짝(GET 간격 µs). 워커 소비자 1개와 8개의 비교 |

### 도구

| 스크립트 | 하는 일 |
|---|---|
| `scripts/evidence.py <이름> [제한 수량] [초당 요청] [지속 초]` | `scenario.py`와 같은 흐름으로 돌린 뒤 기록 전체를 받아, 1단계 리포트 뒤에 원인별 증거를 붙인다. 결과는 `results/evidence-<이름>/`(`report.txt`, `records.json` 등) |
| `scripts/race.py <이름> [반복] [제한 수량] [요청 수]` | 작은 제한 수량(100)으로 짧은 버스트(300건)를 여러 번 돌려 발급이 제한에 닿는 순간을 반복해 만든다. 실행마다 과발급과 같은 값을 읽은 묶음을 센다. 워커 소비자 수는 앱 설정(`WORKER_CONCURRENCY`)을 따른다. 결과는 `results/race-<이름>/` |
| `GET /experiments/records?couponId=C001` | 기록 전체(JSON). 시각은 앱 시계의 epoch 마이크로초 |

리포트의 원인별 증거 읽는 법
- **1차 통과 순번:** 1차 검증 시각 순서로 매긴 번호. "순번 − 1차 때 본 수량"이 그 순간 1차 검증이 못 본, 앞서 통과했지만 아직 세지 않은 요청 수다.
- **발급이 제한에 닿은 시각:** 10,000번째 `INCR`이 실행된 시각. 이 뒤로는 1차 검증도 마감을 돌려준다.
- **같은 수량을 읽은 묶음:** 2차 검증에서 둘 이상의 워커가 같은 값을 읽은 경우. 각자 `INCR`하니 수량은 그만큼 오른다.

- `scenario.py`의 흐름을 `execute()`로 떼어 `evidence.py`가 같이 쓴다.

### 도구

| 도구 | 하는 일 |
|---|---|
| 스위치 `ISSUE_MODE` | 수량을 다루는 방식. `original`(원문 기존, 기본값), `precharge`(시도 1), `lua`(시도 2), `double-counter`(시도 3 + 1, 원문의 최종 선택) |
| `scripts/evidence.py` | 2단계와 같다. `original`이 아니면 원인별 증거 대신 미발급 요청의 기록(1차 때 읽은 값, 선차감 순번)만 붙인다 |
| `scripts/throughput.py <이름> [VU 수] [지속 초]` | 제한 수량을 넉넉히 두고 사용자 100명이 쉬지 않고 요청한다(closed model). 초당 요청 수, 응답 시간, Redis가 명령마다 쓴 시간(`INFO commandstats`)을 적는다. 결과는 `results/throughput-<이름>/` |
| `scripts/redis_bench.sh` | 앱·MQ·DB를 빼고 Redis 혼자 `GET`·`INCR`·원문 스크립트(`EVALSHA`)를 초당 몇 번 처리하나(redis-benchmark). db 1을 쓰고 끝나면 비운다 |

### 바뀐 것

- 수량을 다루는 방식을 `IssueStrategy`로 떼어 네 가지를 바꿔 끼운다(`IssueStrategyConfig`). 앞단은 `admit`(받아들일지), 워커는 `verify`(발급할지)를 부른다.
- 메시지에 선차감 순번(`position`)을, 집계에 `countReq`(`redisRequestCount`)를 더했다.
- Lua 스크립트는 원문에 적힌 것 그대로다(`IssueCountStore.ADMIT_SCRIPT`). Spring Data Redis는 `EVALSHA`로 보내고 스크립트가 없으면 `EVAL`로 올린다.
- **원문에 코드가 없어 복원한 부분.** 원문의 흐름도는 이미지라 글에 적힌 설명으로 세웠다.
  - 시도 1의 워커 검증: "선차감한 순번(`INCR` 결과)이 제한을 넘었는가". 넘었으면 미발급으로 기록하고 `DECR`로 되돌린다. 원문의 "DB 처리 실패 시 롤백"도 같은 `DECR`이지만, 이 실험은 DB 실패를 만들지 않는다.
  - 시도 3의 마감 처리: `countReq`를 `INCR`한 결과가 제한을 넘으면 `DECR`로 되돌린다. 원문이 "`count`와 `countReq`의 차이를 모니터링해 알람"한다고 해서, 두 키가 평소에 같은 값을 가리키게 맞췄다.
- 선차감 방식(`precharge`, `double-counter`)에서는 리포트 시간표의 `발급(Redis)` 열이 워커의 발급이 아니라 앞단이 선차감한 누계다. `◀`의 "그때까지 성공 응답"이 그보다 조금 작게 나올 수 있다(수집기와 k6의 시각 차이).
- 성능은 원문처럼 "방식만 바꿔 같은 부하를 넣었을 때의 처리량"으로 비교한다. 다만 이 노트북에서는 요청 하나의 시간 대부분이 HTTP·Tomcat·Docker 네트워크에 들고 Redis 명령은 µs 단위라, 전체 처리량의 ±5% 차이는 실행마다의 잡음 안이다. 그래서 Redis가 요청 1건당 쓴 시간과 Redis 혼자의 처리량을 함께 본다.

**3단계에서 새로 알게 된 것**
- **원문의 결과가 그대로 나왔다.** 2-A의 미발급 8,269건이 선차감으로 28건(0.28%)이 됐고, Lua와 이중 카운터는 0건이었다. 과발급은 셋 모두 0건. 이중 카운터는 끝에 `count`와 `countReq`가 같았다(10,000).
- **선차감이 남긴 미발급의 정체.** 28건 모두 1차 때 9,990을 읽었고 1차 검증 시각이 6ms 안에 몰려 있었다. 동시에 들어온 요청들이 같은 값을 보고 각자 `INCR`해 순번 10,001~10,028을 받은 것이다. 2-C에서 워커에서 본 "같은 값을 읽은 묶음"이 앞단으로 옮겨 온 모양이다. Time Gap(평균 2.26초)은 2-A와 다르지 않았는데 미발급이 300분의 1로 줄었다. `GET`과 `INCR` 사이에 MQ 전송이 끼지 않고 Redis 왕복 하나만 남아서다.
- **Lua와 이중 카운터가 0건인 이유는 같다.** 비교와 올리기를 Redis가 한 번에 한다. Lua는 스크립트 안에서, 이중 카운터는 `INCR`이 돌려준 값으로 비교해서다. `INCR` 결과는 요청마다 다른 값이라 두 요청이 같은 값을 볼 수 없다.
- **원문의 성능 저하(21%, 8%)는 이 환경에서 확인하지 못했다.** 직접 실행에서는 원문 기존이 2,779/s, 나머지 셋이 1,930~2,107/s로 비슷하게 낮았고, Claude 검증에서는 네 방식이 2,241~2,458/s로 ±5% 안이었다. 실행 사이의 차이가 방식 사이의 차이보다 크다. 요청 하나의 시간이 거의 HTTP·Tomcat·Docker 네트워크에 들고(응답 중앙값 20~40ms) Redis 명령은 µs 단위라서다. 원문의 수치는 Redis가 더 큰 몫을 차지하는 환경의 값으로 본다.
- **Redis 쪽 비용은 분명히 달랐다.** `EVALSHA` 한 번이 26.9µs로 `GET`·`INCR`(1.1~1.6µs)의 약 20배다. 요청 1건당 Redis가 쓴 시간은 Lua 26.9µs, 원문 기존 3.9µs, 이중 카운터 2.8µs, 선차감 2.7µs였다. redis-benchmark에서도 `EVALSHA`는 초당 110k로 `GET`·`INCR`(220k)의 절반이었다. 다만 요청 1건으로 묶으면 Lua(1번)는 명령 2번짜리 방식과 비슷하다.
- **복원한 부분이 결과에 끼친 영향.** 선차감의 과발급 0건은 복원한 워커 검증(순번 > 제한이면 미발급 + `DECR`) 덕이다. 원문의 실제 코드가 다르면 그 28건이 과발급으로 나타날 수도 있다. 이중 카운터의 `count` = `countReq`도 마감 요청의 `countReq`를 되돌린 복원 덕이다.
